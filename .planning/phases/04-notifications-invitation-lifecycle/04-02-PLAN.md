<objective>
**This plan is the Phase 4 tracer.** It wires one path — a real `Notification` row written by Phase 3's
`respond_to_invitation` — all the way through a Pydantic schema, a new FastAPI router, the app's router
registration, the dashboard's fetch, and three new React components, until a creator can see and read it.
It is the thinnest slice that touches every layer this phase will modify, and it is production-quality:
real ownership scoping, real 401 behavior, real i18n in both locales, real automated tests.

Nothing here is a prototype and nothing here is a placeholder. Every line this plan writes survives into
the finished feature; 04-03 and 04-04 expand outward from it rather than replacing it.

**Gate:** 04-03 (polling, mark-read, bounce) and 04-04 (APScheduler sweep) MUST NOT start until this
plan's end-to-end verification passes. Proving the read path end to end on one commit is the entire point
of running it first — if the layering is wrong, it is wrong now, not after ten committed layers.

Purpose: NOTF-01 (the creator sees an indicator when a notification arrives) and NOTF-02 (the notification
displays the sentence and the recipient's optional message) are both read-path requirements. They are the
requirements whose absence makes the rest of Phase 4 pointless.

Output: `NotificationResponse`, `GET /api/notifications`, the registered router, `NotificationBell`,
`NotificationPanel`, `NotificationRow`, the `notifications.*` key set in both locale files, and the
dashboard mount plus mount-time fetch.

<assumption_delta_decision>
Advisory, non-blocking. The phase scope contains optionality cues (`recipient_name` and
`recipient_message` are optional; the message is "the recipient's *optional* message").

- **Primary noun:** `Notification` — a self-contained snapshot row, not a projection of a live
  `Invitation`. Phase 3 already denormalized `invitation_title` onto it at respond time precisely because
  the invitation is destroyed in the same transaction.
- **Decision: `no-change`.** No generalization occurs in this phase. The optionality is not new — both
  columns were already `nullable=True` in Phase 3's `models/notification.py`; this plan surfaces that
  existing optionality in a response schema and a render branch rather than introducing it. There is no
  second source of notifications, no second delivery channel, and no second tenant model. Promoting
  anything would be inventing a generalization the phase does not have.
- **What would force a revisit:** a second notification kind (e.g. "your invitation expired") arriving in
  the same list. At that point `Notification` stops being "the yes-response row" and needs a discriminator,
  and `invitation_title` / `recipient_name` stop being universally meaningful fields.
- **Suggested (not required) invariant test:** a test asserting that every row returned by
  `GET /api/notifications` round-trips through `NotificationResponse` with `recipient_name=None` and
  `recipient_message=None` accepted — so a future non-response notification kind cannot be added by
  quietly making those fields required again.
</assumption_delta_decision>
