## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| Assuming multiple backend replicas | The Railway persistent volume holding `/data/photos` can be mounted by only one active deployment. Any plan that assumes 2+ backend replicas in this milestone silently breaks photo upload (`invitations.py:130`) and photo serving (`routers/photos.py`) on the replicas without the mount — taking down already-shipped Phase 2 and Phase 3 features. Surfaced through analysis during this discussion, not through a production failure. | advisory | Phase 4 plans must target a single backend container. The scheduler's advisory lock (D-19) is forward-looking insurance, not permission to scale. Scaling is gated on INFR-V2-01 (next milestone). |
| Re-litigating the scheduler choice | APScheduler vs Celery/Redis was compared twice this session at the user's request and settled both times. The deciding factor is the volume constraint, not preference. | advisory | Read 04-DISCUSSION-LOG.md § Expiry Cleanup before reopening. The comparison table and the volume argument are recorded there in full. |

<decisions_made>

Full list is in `04-CONTEXT.md` (D-01 to D-23). The ones that shape everything downstream:

- **Top bar heart icon + red dot → dropdown panel.** No count badge, no dedicated route, no inline dashboard section.
- **Opening the panel marks everything read** in one call. Unread items keep their highlight for that session only. Mark-read failures fail silently.
- **Dashboard polls every 30 seconds** for the full notification list; heart does a one-shot bounce when the dot appears. 401 logs out (matching Phase 1 D-03); network errors retry silently.
- **Notifications auto-delete after 30 days** — NOTF-V2-02 pulled forward because the cleanup job is being built anyway. Rated **one-way**: recipient messages exist nowhere else once the invitation is destroyed on respond.
- **APScheduler in the FastAPI lifespan, hourly, guarded by `pg_try_advisory_lock`.** Celery/Redis rejected because a separate worker service cannot mount the Railway volume and so could not delete photo files — failing INV-07 outright.
- **v1 stays single-container with the volume.** Storage Buckets migration + scale-up to 3 replicas move to the next milestone.
- **Expired invitations vanish silently** from the dashboard; photo deletion failures are logged and the DB row is deleted regardless.

Notable: the `Notification` model already exists from Phase 3 (`backend/app/models/notification.py`) with every field needed. No migration is required for the notification feature itself — only for adding `apscheduler` to `backend/pyproject.toml`.
</decisions_made>
