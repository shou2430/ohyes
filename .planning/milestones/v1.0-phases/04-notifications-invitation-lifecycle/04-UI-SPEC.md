# Phase 4 — UI Design Contract

> Visual, interaction, and animation contract for the Notifications & Invitation Lifecycle phase. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope of this contract:** the notification surface only — top bar heart indicator, dropdown panel, notification row, empty state, unread highlight, and the disclosure a11y contract. The INV-07 / NOTF-V2-02 cleanup job is backend-only and has **no UI** (see "Non-UI: Silent Expiry" below).

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none (hand-rolled with Tailwind v4 utilities) |
| Icon library | Lucide React (`lucide-react` ^1.14) |
| Animation library | Motion (Framer Motion) ^12.38 |
| Font | Inter (via `--font-sans` theme token) |

**shadcn gate: resolved without a prompt.** `components.json` is absent and stays absent. CLAUDE.md explicitly rejects component libraries ("Chakra UI / Material UI — add significant bundle weight and constrain styling"), and Phases 1, 2, and 3 all shipped with `Tool: none` and hand-rolled Tailwind. Introducing shadcn in the fourth phase of a deployed app would fork the design system rather than extend it. No user prompt was issued because the decision is already locked upstream.

**No new dependencies.** `lucide-react` supplies `Heart`; `motion` supplies the bounce and panel transition; relative timestamps use the platform's `Intl.RelativeTimeFormat` (no `date-fns`, no `dayjs`).

**Theme tokens are unchanged.** `frontend/src/index.css` `@theme` block requires **zero additions** for this phase.

## Component Inventory

**Focal point:** On the dashboard, the invitation cards remain the focal point (Phase 2). The heart indicator is deliberately a *peripheral* attractor — small, in the top bar chrome, drawing the eye only when the red dot appears. When the panel is open, the panel's topmost notification row is the focal point.

### 1. `NotificationBell` — top bar heart + dot

Mounted in `DashboardPage.jsx` inside the existing right-hand cluster (`<div className="flex items-center gap-2">`, line 90), as the **first** child — before the avatar, name, and logout. It is only ever rendered on the dashboard, which satisfies D-14's "polling on the dashboard only" without a shared context.

**Wrapper:** `<div className="relative">` — the desktop panel anchors to this.

**Button:**
```
type="button"
className="relative inline-flex h-11 w-11 items-center justify-center rounded-full
           text-text-secondary transition-colors hover:bg-cream hover:text-text-primary
           focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-accent focus-visible:ring-offset-2"
```

| State | Heart icon | Dot | Button background |
|-------|-----------|-----|-------------------|
| Resting (0 unread, panel closed) | Lucide `Heart`, `size={20}`, `text-text-secondary`, outline | absent | transparent |
| Hover / focus (any unread state) | `text-text-primary` (or stays `text-accent` if unread) | unchanged | `bg-cream` |
| Unread (>=1 unread, panel closed) | Lucide `Heart`, `size={20}`, `text-accent`, outline (no fill) | present | transparent |
| Panel open | Lucide `Heart`, `size={20}`, `text-text-primary` | absent (cleared optimistically on open) | `bg-cream` |
| Disabled | **never** — D-04: the icon is always clickable, even with zero notifications |

**Red dot:**
```
className="absolute top-2 right-2 h-2 w-2 rounded-full bg-accent ring-2 ring-white"
aria-hidden="true"
```
8px diameter, inset 8px from the button's top-right — which lands its center exactly on the 20px heart glyph's top-right corner inside the 44px button. The 2px white ring separates it from the heart stroke against the white top bar.

### 2. `NotificationPanel` — dropdown container

**Positioning:**

| Viewport | Classes |
|----------|---------|
| < 640px (mobile) | `fixed left-4 right-4 top-[72px]` — full width minus the 16px gutters that match the top bar's `px-4`; 72px = 64px top bar + 8px gap |
| >= 640px (sm+) | `sm:absolute sm:left-auto sm:right-0 sm:top-full sm:mt-2 sm:w-[360px]` — anchored under the heart button, right-aligned, extending leftward |

Same component, two widths. **No bottom sheet, no full-screen overlay, no backdrop scrim** (D-05). The panel does not push the invitation cards down — it overlays them.

> ⚠ **Do not place the panel inside a transformed ancestor.** A CSS `transform` on any ancestor creates a containing block for `position: fixed` descendants, which would silently re-anchor the mobile panel to that ancestor instead of the viewport. The one-shot bounce is therefore specified on a `motion.span` wrapping the heart glyph — a *sibling* of the panel, never a parent. An element's own transform does not affect its own containing block, so the panel's entrance animation is safe; an ancestor's would not be.

**Container:**
```
className="z-40 overflow-hidden rounded-xl border border-border bg-white shadow-lg"
```
`shadow-lg` matches the elevation of the Phase 2 SuccessModal and Toast. `z-40` sits below Toast/Modal (`z-50`) and above page content.

**Panel header** (sticky, gives the scroll region an anchor):
```
className="sticky top-0 border-b border-border bg-white px-4 py-3
           text-sm font-semibold text-text-primary"
```
Text: `notifications.title`. No "mark all read" button — D-08 makes it redundant. No close button — Escape and outside-click handle dismissal, and mobile has generous surrounding tap area.

**Scroll region:**
```
tabIndex={0}
role="region"
aria-label={t('notifications.title')}
className="max-h-[70vh] overflow-y-auto overscroll-contain
           divide-y divide-border sm:max-h-[420px]"
```
`tabIndex={0}` makes the scrollable region keyboard-operable (WCAG 2.1.1) — required because notification rows contain no focusable children. `overscroll-contain` prevents scroll chaining to the page body on mobile.

**No loading state, ever.** D-15: the poll already holds the full list, so the panel always opens with data (or with the empty state). Do not render `LoadingSpinner` inside the panel.

### 3. `NotificationRow`

One row per notification, newest first (D-06). Non-interactive — no click target, no hover state, no per-item dismiss (deferred).

```
className={`border-l-2 px-4 py-3 ${
  isHighlighted ? 'border-l-accent bg-cream' : 'border-l-transparent bg-white'
}`}
```
The `border-l-2` is present in **both** states (transparent when read) so the 2px never causes a content shift between states.

**Content, top to bottom:**

1. **Sentence** — `text-sm text-text-primary` (line-height 1.5, wraps freely; no truncation, no `line-clamp`). Safe to leave unclamped **only because the inputs are now bounded at the source** — see "Cross-Phase Amendment" below. Do not remove that cap without revisiting this rule.
   - With a name: `notifications.saidYes` → `"{{name}} said yes to your “{{title}}”"`
   - Name null or empty string: `notifications.saidYesAnonymous` → `"Someone said yes to your “{{title}}”"`
   - `recipient_name` is nullable in `backend/app/models/notification.py` (the recipient can use "Skip message"), so the anonymous branch is required, not optional.
   - **No inline bold on the name.** Rendered as a single interpolated string, deliberately avoiding `<Trans>` markup — it keeps both zh-TW and en translations natural sentences and keeps Phase 5's i18n pass simple. Hierarchy in the row comes from the message quote and the secondary-colored timestamp.
   - Preceded by an `sr-only` "New" marker when highlighted: `<span className="sr-only">{t('notifications.newLabel')} </span>`.

2. **Message quote** — rendered **only** when `recipient_message` is a non-empty string:
   ```
   className="mt-2 border-l-2 border-border pl-3 text-sm text-text-secondary"
   ```
   Max 30 characters by DB constraint, so it never needs truncation. **No italics** — synthesized oblique renders poorly for zh-TW CJK glyphs. The left rule carries the quotation semantics; no quotation marks are added.

3. **Relative timestamp** — `mt-2 text-sm text-text-secondary`, wrapped in `<time dateTime={iso} title={absoluteLocalString}>`.

**Row height varies** (2 to ~4 content lines in the worst case, more for zh-TW). This is accepted — volume is low and dividers (`divide-y divide-border`) carry the rhythm. Height is bounded by the input caps in the Cross-Phase Amendment, not by any truncation in this component.

### 4. Empty state (inside the panel)

Shown when the list is empty. The panel still opens; the heart is never disabled or hidden (D-04).

```
<div className="px-4 py-6 text-center">
  <Heart size={32} className="mx-auto text-border" strokeWidth={1.5} />
  <p className="mt-3 text-base font-semibold text-text-primary">{t('notifications.emptyHeading')}</p>
  <p className="mt-2 text-sm text-text-secondary">{t('notifications.emptyBody')}</p>
</div>
```
`mt-3` = 12px, a multiple of 4. Tone matches the Phase 1 dashboard empty state ("No invitations yet" / "Create your first invitation and share it with someone special.").

### 5. Non-UI: Silent Expiry (INV-07 / D-23)

**There is no UI for invitation expiry.** Expired invitations simply stop appearing in `GET /api/invitations`, so their cards vanish on the next dashboard load. Explicitly do **not** build:
- an "expired" card variant, tombstone, or ghost row
- a toast, banner, or modal on expiry
- a removal animation (there is no client-side event to hook — the card is absent on first render of the next session)

The Phase 2 days-remaining countdown (`dashboard.daysRemaining`) is the creator's only and sufficient advance warning. It is unchanged.

Notification retention (30-day sweep, D-07) is likewise invisible: old rows are simply absent from the next poll response.

## Cross-Phase Amendment — Input Length Caps

**This section modifies Phase 2 and Phase 3 surfaces.** It is recorded here because Phase 4 is what surfaced the defect and what depends on the fix. The planner must include it in the Phase 4 plan.

### Why

The notification sentence interpolates two user-supplied strings — a creator's invitation title and a recipient's name. Audit of the shipped code found the title has **no length constraint at any layer**, and the name is capped so loosely it may as well be unbounded:

| Field | Layer | File | Before |
|-------|-------|------|--------|
| Title | DB column | `backend/app/models/invitation.py:17` | `String(255)` |
| Title | Request schema | `backend/app/schemas/invitation.py` | no `max_length` validator |
| Title | Form input | `CreateInvitationPage.jsx:170` | no `maxLength` attribute |
| Name | DB column | `backend/app/models/notification.py` | `String(100)` |
| Name | Request schema | `InvitationRespondRequest` | `max_length=100` |
| Name | Form input | `MessageCard.jsx:66` | `maxLength={100}` |

A 255-character title plus a 100-character name yields a ~355-character sentence. In the 343px mobile panel at 14px that is roughly 7 lines of Latin text and up to ~13 lines of zh-TW CJK — a single notification would fill the entire panel. The "no truncation" rule in `NotificationRow` is only defensible once both inputs are bounded.

**User decisions (2026-08-02):**
- Cap the **title at 100 characters** with an in-place counter, rather than clamping the notification row. Fixing it at the source protects every surface that renders a title — the dashboard card, the recipient reveal page, and the notification row — not just this phase.
- Cap the **recipient name at 20 characters**. After the title cap, the name became the larger contributor to sentence length; 20 is generous for a real name.
- The **recipient message stays at 30** characters — already enforced at all three layers, unchanged.

> **Accepted tradeoff on the 20-character name.** The field is labelled as a name, but nothing stops a recipient treating it as a free-text greeting ("住在隔壁的王先生和王太太"). At 20 characters that style of input is truncated. This was raised and accepted when the cap was chosen — the counter makes the limit visible before the user hits it.

### Contract — invitation title (100)

**Backend** — `backend/app/schemas/invitation.py`, on the invitation-create request model:
```python
title: str = Field(..., min_length=1, max_length=100)
```
No Alembic migration: the column is already `String(255)`, and 100 < 255. Existing rows longer than 100 are not rewritten — the 7-day TTL plus the 2-invitation-per-user limit means any such row disappears on its own within a week.

**Frontend** — `CreateInvitationPage.jsx`, title `<input>` (line 170): add `maxLength={100}`.

**In-place counter** — reuse the shipped pattern from `MessageCard.jsx:86-88` verbatim, placed after the input and before the existing error paragraph:
```jsx
<p className="mt-1 text-right text-sm text-text-secondary" aria-live="polite">
  {title.length}/100
</p>
```

**Ordering when both the counter and an error are present:** counter first, then `errors.title`. The error paragraph keeps its own `mt-1`, so an errored field shows counter and error stacked — matching how the recipient form already behaves.

### Contract — recipient name (20)

**Backend** — `backend/app/schemas/invitation.py`, `InvitationRespondRequest`:
```python
name: str | None = Field(None, max_length=20)
```
No migration: `notifications.recipient_name` stays `String(100)`, and 20 < 100.

**Frontend** — `MessageCard.jsx:66`, name `<input>`: `maxLength={100}` → `maxLength={20}`.

**In-place counter — newly added to the name field.** The name input currently has **no** counter, which was fine at 100 (nobody reaches it) but is not fine at 20, where users will hit the limit and need to see why input stopped. The sibling message field at 30 already has one, so adding it here is consistency rather than invention:
```jsx
<p className="mt-1 text-right text-sm text-text-secondary" aria-live="polite">
  {name.length}/20
</p>
```

> This counter is an **implementation judgment**, not part of the user's stated decision. The instruction was the 20-character cap; a silent cap with no counter would be a worse experience than the field it sits next to. Flag it back if you disagree — removing it is a one-line change.

### Shared rules for all three counters

Token compliance: `text-sm` is the existing Body role, `text-text-secondary` is an existing token, `mt-1` is 4px. Zero new tokens, zero new dependencies, no new i18n keys.

**No hard-stop styling.** `maxLength` makes the over-limit character unreachable, so the counter does **not** turn red or destructive on approach — it can never be exceeded. This matches the shipped `MessageCard`, which has no warning state at 30/30.

### Resulting bound on the notification sentence

| | Title | Name | Worst-case sentence | Lines at 375px |
|---|-------|------|--------------------|----------------|
| Before | 255 | 100 | ~355 chars | ~7 Latin / ~13 zh-TW |
| After | 100 | 20 | ~137 chars | ~3 Latin / ~6 zh-TW |

Bounded, scrollable, and no longer able to fill the panel with a single item.

## Interaction Contracts

### Open the panel

1. User clicks/taps the heart button (or presses Enter/Space while it is focused).
2. Panel mounts and animates in (see Animation Specifications).
3. **Snapshot the highlight set before anything else:** `highlightedIds = notifications.filter(n => !n.is_read).map(n => n.id)`, stored in component state for this open only.
4. Optimistically clear the red dot: set every local notification's `is_read` to `true`.
5. Fire the mark-read request (D-08 — one call for everything, no per-item action).
6. Move focus to the panel scroll region.

No loading state at any point in this sequence.

### Unread highlight and its session decay (D-09)

- The highlight set is captured **once per open**, at step 3 above, from the state that existed before step 4's optimistic flip.
- While the panel stays open, the highlight does **not** change, fade, or animate away. A decaying highlight would read as a rendering bug.
- On the **next** open, step 3 runs against a list where `is_read` is already `true` for those items, so `highlightedIds` is empty and they render in the plain style.
- Read state is visual only: nothing is hidden, moved, reordered, or collapsed (D-09).
- If a *new* notification arrives via poll while the panel is open, it appears at the top of the list **without** highlight (it was not in the snapshot) and the dot does not reappear until the panel is closed and the next poll runs. Accepted: this edge is vanishingly rare at v1 volume and keeps the snapshot rule single-sourced.

### Mark-read failure (D-10)

Fails silently. No toast, no revert, no retry, no console-visible user feedback. The dot naturally reappears on the next 30-second poll because the server still has `is_read = false`. This is deliberately different from the delete/copy flows, which do toast on failure (Phase 2 D-18) — those are user-initiated, this is not.

### Dot appears (D-16)

**Dot visibility is exactly:**
```
showDot = unreadCount > 0 && !panelOpen
```
State this explicitly in the implementation. Without the `&& !panelOpen` term, the optimistic clear (open step 4) and the 30-second poll fight over the dot: a notification arriving after the mark-read call is genuinely unread server-side, so the next tick while the panel is still open would re-raise the dot underneath the open panel.

When the derived unread count transitions from `0` to `>0` (poll tick or first load), the heart plays a **one-shot** spring bounce and the dot scales in. Once per transition — never on every poll tick, never while the count merely grows from 1 to 2.

No toast, no sound, no `document.title` change (D-12 — the title stays "Dashboard - OhYes"), no browser Notification API.

### Close the panel

The panel closes, focus returns to the heart button, and the exit animation plays on any of:

| Trigger | Detail |
|---------|--------|
| Heart button click | Toggles closed |
| `Escape` keydown | Listener on `document` while open; `preventDefault` so it does not bubble into anything else |
| Pointer down outside | `pointerdown` listener on `document`; ignore events whose target is inside the wrapper (panel or button) |
| Focus leaves the wrapper | `focusout` on the wrapper where `relatedTarget` is outside it — covers Tab-away, since the panel is non-modal |
| Route change | Unmounting `DashboardPage` tears down the panel and stops the poll (D-14) |

**No focus trap.** The panel is a non-modal disclosure containing static content; trapping focus would strand keyboard users. Escape + focusout is the correct pattern.

### Polling (D-13, D-14, D-15, D-17)

- `setInterval` 30 000 ms, started on `NotificationBell` mount, cleared on unmount. Because the bell only mounts inside `DashboardPage`, this satisfies "dashboard only, not `/create`, not lifted into a shared context."
- Each tick fetches the **full** list (`GET /api/notifications`) with the `Authorization: Bearer` header from `localStorage.getItem("ohyes_token")`, matching the existing dashboard fetch pattern.
- Unread count is derived client-side: `notifications.filter(n => !n.is_read).length`. It is never rendered as a number — no badge (D-02) — only as the dot's presence and in the button's `aria-label`.
- **401:** clear `localStorage` and redirect to `/` (Phase 1 D-03).
- **Network error:** ignored silently, retried on the next tick. No toast, no backoff, no circuit breaker, no offline indicator.
- Timestamps re-derive on each render, so the 30-second tick refreshes them for free. Do not add a second timer for the clock.

### Relative timestamp formatting

Native `Intl.RelativeTimeFormat(i18n.language, { numeric: 'auto' })` — zero dependencies, correct for both `zh-TW` and `en`.

| Age | Rendering |
|-----|-----------|
| < 60 s | `notifications.justNow` (a literal key, not `Intl`, to avoid the bare "now" string) |
| < 60 min | `rtf.format(-minutes, 'minute')` — "5 minutes ago" / "5 分鐘前" |
| < 24 h | `rtf.format(-hours, 'hour')` — "2 hours ago" / "2 小時前" |
| < 7 days | `rtf.format(-days, 'day')` — "3 days ago" / "3 天前" |
| >= 7 days | `Intl.DateTimeFormat(i18n.language, { month: 'short', day: 'numeric' })` — "Jul 30" / "7月30日" |

The 30-day retention window (D-07) bounds the maximum age, so no year is ever needed. `created_at` is timezone-aware from the backend; parse the ISO string directly.

## Animation Specifications

All Motion (Framer Motion) 12.x. Every animation in this section is skipped when `prefers-reduced-motion: reduce` — the dot and panel then appear and disappear instantly.

### Heart one-shot bounce (on dot appearance)
```
animate: { scale: [1, 1.25, 0.92, 1.08, 1] }
transition: { duration: 0.6, ease: "easeOut", times: [0, 0.25, 0.5, 0.75, 1] }
```
Applied to a `motion.span` wrapping the `Heart` glyph, not to the button (the button's 44px hit area must not move). Keyed off a counter that increments only on the `0 -> >0` transition so the keyframe array replays exactly once.

### Red dot entrance
```
initial:    { scale: 0 }
animate:    { scale: 1 }
transition: { type: "spring", stiffness: 500, damping: 15 }
```
Matches the Phase 3 dodge-counter badge entrance family (spring, stiffness 400–500, damping 15).

### Red dot exit (on panel open)
```
exit:       { scale: 0, opacity: 0 }
transition: { duration: 0.15 }
```
Via `AnimatePresence`.

### Panel open / close
```
initial:    { opacity: 0, y: -8, scale: 0.98 }
animate:    { opacity: 1, y: 0,  scale: 1 }
exit:       { opacity: 0, y: -8, scale: 0.98 }
transition: { duration: 0.15, ease: "easeOut" }
style:      { transformOrigin: "top center" }        // mobile
style:      { transformOrigin: "top right" }         // sm+ — matches the anchor
```
Wrapped in `AnimatePresence` so the exit plays. Deliberately fast (150ms) — this is chrome, not a moment. Contrast with the Phase 3 screen transitions at 400ms.

### Row entrance
**None.** Rows render statically when the panel opens. A staggered list entrance would fight the 150ms panel transition and delay reading. New rows arriving via poll while the panel is open also appear without animation.

### Reduced motion
```
const reduce = useReducedMotion();   // from "motion/react"
```
- Bounce: skipped entirely (no scale keyframes).
- Dot entrance/exit: `transition: { duration: 0 }`.
- Panel: `transition: { duration: 0 }`, no `y` or `scale` offsets — opacity 1 immediately.

**Copy notes for the translator/executor:**

- `{{count}}` in `notifications.ariaUnread` uses i18next interpolation, not pluralization — zh-TW has no plural forms and the en string reads correctly for 1 ("1 unread").
- Do not add a "Mark all as read" string. D-08 makes the action implicit.

- **Do not change `recipient.namePlaceholder` or `recipient.nameLabel`** to advertise the 20-character limit. The counter carries that information; duplicating it in the label would crowd a field that is already tight at 375px.

## Responsive Behavior

Mobile-first. 375px is the minimum supported viewport.

| Breakpoint | Layout |
|------------|--------|
| 375–639px (mobile) | Heart button 44x44, first in the top bar right cluster. Panel is `fixed`, spanning `left-4 right-4` (343px wide at 375px) at `top-[72px]`. Max height `70vh` with internal scroll. Panel horizontally aligned to the page gutters, not to the button. Transform origin: top center. |
| >= 640px (sm) | Panel becomes `absolute`, `w-[360px]`, anchored `right-0 top-full mt-2` on the button wrapper, extending leftward. Max height `420px`. Transform origin: top right. Top bar gutter becomes `px-8` (existing). |
| >= 1024px (lg) | No further change. The panel is already at its terminal size. |

At 375px the notification sentence wraps to at most ~3 lines of Latin text (~6 lines of zh-TW) in the worst case, given the 100-character title cap and the 20-character name cap. Wrapping is expected and unstyled — no truncation, no `line-clamp`, no ellipsis. Recipient messages are DB-capped at 30 characters and never wrap past 2 lines.

The heart button and its 44px target are identical at every breakpoint — the panel is the only responsive element.

## Accessibility

**Disclosure pattern (not a menu).** The rows are static content, not actionable items, so `role="menu"` / `role="menuitem"` would be wrong (they promise arrow-key navigation and activation that do not exist).

| Concern | Contract |
|---------|----------|
| Trigger semantics | `<button type="button">` with `aria-expanded={open}` and `aria-controls="notification-panel"` |
| Trigger name | `aria-label` from `notifications.title` (0 unread) or `notifications.ariaUnread` with count (>=1 unread). The button is icon-only and has no visible text. |
| Panel semantics | `<div id="notification-panel">`; the scroll region carries `role="region"` and `aria-label={t('notifications.title')}` |
| Focus on open | Moves to the panel scroll region (`tabIndex={0}`), making Escape and focusout behave naturally |
| Focus on close | Returns to the heart button in every close path (Escape, outside click, toggle, focusout-to-outside) |
| Focus trap | **None.** Non-modal disclosure — trapping would strand keyboard users. |
| Escape | Closes the panel, returns focus to the button |
| Tab | Not intercepted. Tabbing out of the wrapper closes the panel via `focusout`. |
| Scrollable region keyboard access | `tabIndex={0}` on the overflow container (WCAG 2.1.1) — required because rows contain no focusable children |
| Focus visible | `focus-visible:ring-2 focus-visible:ring-accent focus-visible:ring-offset-2` on the heart button, matching the Phase 1 focus contract |
| Decorative elements | Red dot: `aria-hidden="true"`. Empty-state `Heart` icon: `aria-hidden="true"`. |
| Unread conveyed non-visually | `sr-only` "New" prefix inside each highlighted row's sentence, plus the count in the button's `aria-label` |
| Live regions | **Deliberately none.** A polling `aria-live` region would announce every 30 seconds and interrupt screen-reader users. New notifications are discovered when the user next focuses the heart button, whose `aria-label` carries the count. This is a considered restraint, not an omission. |
| Timestamps | `<time dateTime={isoString} title={absoluteLocalString}>` so assistive tech and hover both expose the exact time behind the relative phrasing |
| Touch targets | Heart button 44x44 on all viewports. Rows are non-interactive and therefore exempt. |
| Reduced motion | `prefers-reduced-motion: reduce` disables the bounce, the dot spring, and the panel transition (see Animation Specifications) |
| Contrast | All combinations meet WCAG AA — see the Color section |
| Language | Panel content inherits the document language from i18next; no `lang` attribute overrides needed |
