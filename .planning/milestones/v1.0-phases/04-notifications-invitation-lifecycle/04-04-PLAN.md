<objective>
Make INV-07 real: a scheduled in-process sweep that actually deletes expired invitations (DB row plus the photo file on the Railway volume) and prunes notifications past their retention window — replacing the current situation where expired invitations are merely filtered out of queries and their photos live on the volume forever.

Purpose: an invitation's 7-day TTL is a product guarantee (D-21) and the volume is finite. Lazy deletion on query was explicitly rejected in D-18 because a creator who stops logging in would never trigger it. The same job also implements NOTF-V2-02 pulled forward per D-07, at the cost of one extra DELETE statement.

Output: `backend/app/tasks/cleanup.py` (advisory-lock-guarded `run_cleanup()` per D-19, hourly per D-20), the `AsyncIOScheduler` wiring in the existing `main.py` lifespan per D-18, `backend/tests/test_cleanup.py`, and the NOTF-V2-02 reclassification in `.planning/REQUIREMENTS.md`. No UI ships (D-23), and no photo-removal failure stops the sweep (D-22).

**`autonomous: false`** — D-07 is rated **one-way** in `04-CONTEXT.md`: deleted notification rows carry recipient messages that exist nowhere else, because the invitation was already destroyed when the recipient responded. Task 2 is a blocking `checkpoint:decision` that must be answered before the destructive notification sweep is implemented.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| scheduler process → PostgreSQL | The sweep issues unauthenticated-by-user, whole-table DELETE statements with no request context and no `current_user` scoping. A wrong `WHERE` clause here destroys data no endpoint could reach. |
| database row → filesystem | `photo_filename` is read out of the DB and joined onto `PHOTO_STORAGE_PATH` to build a path that is then passed to `os.remove`. The DB value crosses into filesystem-command territory. |
| container instance ↔ container instance | Multiple Uvicorn workers or (post-milestone) multiple Railway replicas each run their own scheduler against one shared database and one shared volume. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-SILENT | Denial of Service | `run_cleanup()` / `main.py` lifespan | high | mitigate | A sweep that never starts, throws on the first tick, or is permanently lock-blocked leaves expired invitations and their photos on the volume past their TTL — INV-07 fails silently while every test and build stays green. Mitigation: every invocation emits a log record on the `app.tasks.cleanup` logger — the lock-skip line at INFO, or the completion line naming invitations deleted / photo files removed / notifications deleted — so absence of the line in Railway logs is the detection signal. Task 4's `test_scheduler_registers_hourly_cleanup_job` proves the job is actually registered rather than assumed. |
| T-04-LOCKKEY | Denial of Service | `CLEANUP_LOCK_KEY` in `cleanup.py` | high | mitigate | An advisory-lock key that collides with a future feature's key means `pg_try_advisory_xact_lock` returns false forever and the sweep never deletes anything — the same silent failure as T-04-SILENT, with no error to observe. Mitigation: one distinctive constant (`CLEANUP_LOCK_KEY = 727100401`) defined in exactly one module, carrying a comment that it is the project-wide cleanup key and must not be reused. Any future advisory lock must pick a different value. |
| T-04-PATH | Tampering | `_remove_photo_files()` | medium | mitigate | `photo_filename` is joined onto `settings.PHOTO_STORAGE_PATH` and handed to `os.remove`. A filename containing path separators or `..` would escape the volume directory. Mitigation: the value is server-generated at upload time (Phase 2) and constrained to `String(255)`, never taken from the request in this phase; the path is built with `pathlib.Path` joining (not string concatenation) exactly as the existing `delete_invitation` does, and removal is wrapped in `try/except OSError`. Residual risk accepted at ASVS L1 — a stricter control would validate the resolved path stays under `PHOTO_STORAGE_PATH`. |
| T-04-XACT | Denial of Service | advisory lock acquisition | medium | mitigate | A session-scoped advisory lock taken on a pooled connection can be stranded when the connection is recycled without an explicit unlock, freezing the sweep permanently (RESEARCH Pitfall 1). Mitigation: use the transaction-scoped lock function, which releases at COMMIT/ROLLBACK; `test_advisory_lock_blocks_concurrent_run` proves the guard engages, and the single `db.commit()` proves it releases. |
| T-04-DBLRUN | Tampering | multi-worker / multi-replica scheduler | medium | mitigate | Two schedulers firing the same tick could interleave a DELETE and a file removal against the same rows. Mitigation: the advisory lock serializes runs across processes and instances (D-19), which is precisely why D-19 required it even though v1 runs a single container. |
| T-04-INFO | Information Disclosure | cleanup log lines | low | accept | Log lines name photo filenames and row counts, not recipient names or message bodies. Accepted: filenames are opaque server-generated identifiers and the counts carry no personal data. |
| T-04-SC | Tampering | package installs | low | transfer | This plan installs no packages. `apscheduler` is added to `backend/pyproject.toml` by 04-01 (wave 0), which owns the package-legitimacy verification for it; Task 4 only asserts the import succeeds and halts if it does not. |

## Decision deviations

**D-19 names the session-scoped advisory-lock function; this plan uses the transaction-scoped one.** D-19's binding requirement is the behavior — "the job wraps each run in a PostgreSQL advisory lock with a fixed key; an instance that cannot acquire the lock skips that tick" — and its own stated framing is that "the lock is local to the job function". `pg_try_advisory_xact_lock` delivers exactly that and auto-releases at COMMIT, whereas the session-scoped variant can be stranded on a recycled pooled connection (RESEARCH Pattern 2 and Pitfall 1) and would freeze the sweep permanently. The lock key value and the logging format are already explicitly Claude's discretion in `04-CONTEXT.md`. No requirement of D-19 is reduced; the deviation is in the function name only and is recorded here for traceability.
