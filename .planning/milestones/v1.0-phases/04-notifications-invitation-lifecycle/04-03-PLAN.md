## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Creator browser -> Notifications API | Authenticated Bearer-JWT request; the server must never trust a client-supplied identity field |
| Poll timer -> Backend | Automated, unattended periodic fetch; must fail closed on auth expiry (401) rather than fail open |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-IDOR | Tampering / Elevation of Privilege | `POST /api/notifications/read` | high | mitigate | UPDATE's WHERE clause filters on `Notification.user_id == current_user.id`; the route accepts no request body, so no `user_id` can ever arrive from the client; `test_mark_all_read_scoped_to_owner` proves a second owner's unread rows are untouched. |
| T-04-POLL-DISC | Information Disclosure | `GET /api/notifications` poll response | low | accept | Already authenticated + owner-scoped by 04-02; polling adds no new exposure — recipient name/message travel over the same Bearer-authenticated channel as the rest of the dashboard. |
| T-04-POLL-DOS | Denial of Service | 30s full-list poll, no `limit`/pagination | low | accept | D-07's 30-day notification TTL and the 7-day invitation TTL bound list growth; v1 traffic is low per CLAUDE.md's stated constraints (max 2 invitations/user). Revisit if volume grows before pagination ships. |
| T-04-SILENT-FAIL | Repudiation | Silent mark-read failure (D-10) | low | accept | Deliberate UX decision — the server remains the source of truth and the dot self-heals on the next 30s poll, so no audit gap that matters at v1 scale. |

No new package installs in this plan (Motion, lucide-react, react-i18next, SQLAlchemy are already dependencies) — the package-legitimacy gate does not apply here.
</threat_model>
